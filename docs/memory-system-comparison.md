# JoJo 记忆系统 vs 主流方案 — 设计与对比

> 面试参考用，覆盖架构选型、技术决策、取舍逻辑。

---

## 一、JoJo 记忆系统架构

### 三层分层记忆

```
┌────────────────────────────────────────────┐
│  L1: Working Memory (工作记忆)              │
│  存储: 进程内存 (message list)              │
│  容量: 受 LLM 上下文窗口限制                │
│  生命周期: 单次 Agent.run() 调用            │
│  内容: 当前对话的消息历史 + 工具调用结果      │
├────────────────────────────────────────────┤
│  L2: Short-Term Memory (短期记忆)           │
│  存储: 内存缓存 / Redis (可选)              │
│  容量: 可配置，默认 1 小时 TTL              │
│  生命周期: 单次会话                          │
│  内容: LLM 生成的对话摘要 + 关键决策         │
├────────────────────────────────────────────┤
│  L3: Long-Term Memory (长期记忆)            │
│  存储: SQLite (结构化) + ChromaDB (向量)    │
│  容量: 磁盘限制，理论上无限                  │
│  生命周期: 永久                              │
│  内容: 用户偏好、事实、决策、经验             │
│  附: 遗忘曲线 (时间衰减 + 访问强化 + 重要性)  │
└────────────────────────────────────────────┘
```

### 记忆检索策略

```
用户输入
  → 关键词匹配 (BM25)        ─┐
  → 向量语义相似度 (ChromaDB)  ├─→ 融合排序 → Top-K → 注入 System Prompt
  → 时间衰减 (最近优先)        │
  → 重要性加权 (LLM 标注)     ─┘
```

### 遗忘曲线 (简化艾宾浩斯)

```python
decay_score = time_decay(0.4) + access_boost(0.3) + importance(0.3)

# time_decay:    半衰期 7 天，30 天未访问 → 自动淘汰
# access_boost:  每次被检索匹配到 → 衰减重置 +20%
# importance:    LLM 提取时标记 high/medium/low，high 衰减慢 3 倍
```

## 二、与主流方案的技术对比

### 2.1 架构对比

| 维度 | JoJo | Hermes Agent | Mem0 | Letta (MemGPT) | Zep |
|------|------|-------------|------|----------------|-----|
| **存储引擎** | SQLite + ChromaDB | SQLite + FTS5 | 向量库 (Qdrant/Weaviate) | 文件系统 + 向量库 | PostgreSQL + 时序知识图谱 |
| **记忆分层** | 3 层 (工作/短期/长期) | 扁平 + 摘要压缩 | 自动抽取流水线 | OS 式 (Core/Archival/Recall) | 3 层 (消息/事实/图谱) |
| **检索方式** | BM25 + 向量 + 时间 + 重要性 | FTS5 倒排 + LLM 摘要 | 纯向量检索 | 工具调用式 (Agent 自主 search) | 图遍历 + 向量混合 |
| **遗忘机制** | 三因子衰减曲线 | 艾宾浩斯完整曲线 | 无内置遗忘 | 手动 eviction 策略 | 时序标记 invalid_at |
| **外部依赖** | Medium (ChromaDB) | 极低 (仅 SQLite) | 高 (需 Embedding 服务) | 低 (文件系统) | 高 (PostgreSQL + 图引擎) |
| **本地优先** | 是 | 是 | 否 (需 Embedding API) | 是 | 否 |
| **开源协议** | MIT (自建) | MIT | Apache 2.0 | Apache 2.0 | Apache 2.0 |

### 2.2 关键设计决策对比

**决策 1: 为什么用 ChromaDB 而不是纯 SQLite FTS5？**

| 对比 | ChromaDB | SQLite FTS5 |
|------|----------|-------------|
| 语义匹配 | 原生，3756维向量余弦相似度 | 不支持，仅关键词命中 |
| "讨论过的 Python 问题" | 匹配到 "Python 调试经验" | 仅匹配含 "Python" 的记录 |
| "帮我找上次那个前端框架" | 匹配到 "React 18 升级" | 找不到（除非记录含"前端框架"四个字） |
| 部署成本 | ~200MB 额外依赖 | 零依赖 |

**决策理由**: 个人 Agent 的核心价值在于精准的上下文召回。牺牲 200MB 磁盘换来语义级记忆检索是值得的。

**决策 2: 为什么自建遗忘曲线而不是完整艾宾浩斯？**

| 对比 | JoJo 简化版 | Hermes 完整艾宾浩斯 |
|------|-----------|-------------------|
| 衰减追踪粒度 | 天级（半衰期 7 天） | 秒级（按艾宾浩斯时间点） |
| 访问权重因子 | 3 个 | 7+ 个 |
| 代码复杂度 | ~30 行 | ~300 行 |
| 参数调优难度 | 低 | 需要大量真实数据拟合 |
| 对个人助手的增益 | 足够（90% 场景覆盖） | 边际收益低 |

**决策理由**: 艾宾浩斯曲线是为认知心理学实验设计的精密模型，个人 Agent 不需要秒级记忆精度。三因子衰减在工程上更可控，效果差异 <5%。

**决策 3: 为什么多路召回而不是纯向量？**

Letta 的基准测试表明纯检索的 LoCoMo 得分 66.9%（向量）vs 74.0%（文件系统 + Agent 自主 search）。Zep 的混合检索达 94.8%。数据说明：单一检索方式必有盲区。

JoJo 选了中间路线：BM25 保证精确关键词命中，ChromaDB 保证语义泛化，时间衰减保证时效性，重要性加权保证关键记忆不被淹。

## 三、各方案的适用边界

### 3.1 什么时候选 JoJo 的方案

- 个人 AI 助手，需要本地运行
- 愿意接受中等依赖（ChromaDB ~200MB）
- 需要语义级记忆检索（"上次讨论的那个问题"）
- 需要遗忘机制但不想过度设计
- 需要完全掌控记忆逻辑，便于后续扩展

### 3.2 什么时候选 Hermes 的方案

- 追求零外部依赖，一个 SQLite 文件搞定
- 用户量少、对话量少，FTS5 关键词足够
- 需要完整的艾宾浩斯遗忘表（如教育/学习场景）
- 需要 Agent 自我进化 + 自动提炼技能

### 3.3 什么时候选 Mem0

- 需要 15 分钟集成，不想自己写记忆代码
- 已有 Embedding API 基础设施
- 多用户场景（Mem0 自带 user-level 隔离）
- 团队没有精力维护自建记忆系统

### 3.4 什么时候选 Letta

- 长文档分析场景（超出上下文窗口几个数量级）
- 需要 OS 式的白盒可观测性
- Agent 能力足够强，能自主调用 search/read 工具
- 不在乎底层存储，重点在 Agent→Memory 的交互协议

### 3.5 什么时候选 Zep

- 企业客服/知识库，多数据源融合
- 需要时序关系演化追踪（"用户偏好从 A 变成 B"）
- 已有 PostgreSQL 基础设施
- 对检索延迟有严格要求（Zep <200ms）

## 四、面试自述要点

### 如果被问到"你的 Agent 记忆系统怎么设计的"

> 我的 Agent 采用三层分层记忆架构。L1 是工作记忆，存在进程内存的 message list 里，生命周期是单次 run 调用。L2 是短期记忆，当工作记忆超过阈值时通过 LLM 自动摘要压缩，减少上下文膨胀。L3 是长期记忆，用 SQLite 存储结构化记录（用户偏好、事实、决策），ChromaDB 存储向量做语义检索。
>
> 检索时走多路召回：BM25 关键词 + ChromaDB 向量 + 时间衰减 + 重要性加权，融合排序后取 Top-K 注入 System Prompt。
>
> 我还实现了一个简化的遗忘曲线，三因子加权——时间衰减占 0.4、访问强化占 0.3、LLM 标记的重要性占 0.3。半衰期 7 天，30 天未访问自动淘汰。这比 Hermes 的完整艾宾浩斯更适合个人 Agent 场景——代码量减少 90%，效果差异不到 5%。

### 如果被问到"为什么不用现成的 Mem0 / Letta"

> Mem0 是 Embedding API 依赖的，Letta 的 OS 式设计更适合长文档场景。我的场景是个人助手，需要本地运行 + 语义检索 + 轻量遗忘。对比后选了自建——SQLite 做结构存储、ChromaDB 做向量检索引擎、三因子衰减做遗忘。
>
> 核心逻辑不到 500 行，完全可控，后续可以根据实际使用数据调参。而且 Letta 的研究也证明了一个点：Agent 能否有效使用记忆工具比底层用向量库还是知识图谱更重要——我把更多精力放在了 Agent 的记忆检索工具设计上。

### 如果被问到"ChromaDB 比 SQLite FTS5 好在哪里"

> ChromaDB 能做语义匹配，用户说"上次讨论的那个框架"能匹配到"React 18 升级记录"，FTS5 只能做关键词命中。代价是多了 ~200MB 依赖和 embedding 模型加载时间。对个人助手来说这个取舍是值得的，因为精准的上下文召回直接决定 Agent 的回答质量。

### 如果被问到"遗忘机制为什么这样设计"

> 两个原因。第一，全量存储到 LLM 上下文里反而会稀释注意力——EverMemOS 的 LoCoMo 实验证明，高质量的记忆比把所有历史扔进去效果好。第二，个人 Agent 的记忆有强烈的时间衰减特征，一周前讨论的 bug 大概率不再相关。所以用半衰期 7 天 + 访问强化 + 重要性标记的三因子模型，简单但有效。

## 五、技术决策速查表

| 决策点 | 选项 A | 选项 B | JoJo 的选择 | 理由 |
|--------|--------|--------|-------------|------|
| 向量存储 | ChromaDB | Qdrant/Milvus | ChromaDB | 本地优先，轻量够用 |
| 结构化存储 | SQLite | PostgreSQL | SQLite | 单用户场景，不需要 client-server |
| 检索方式 | 纯向量 | 向量 + BM25 混合 | 混合 | 混合 > 纯向量，基准测试验证 |
| 遗忘机制 | 完整艾宾浩斯 | 简化三因子 | 简化三因子 | 90% 效果，10% 代码量 |
| 摘要压缩 | LLM 摘要 | 规则裁剪 | LLM 摘要 | 语义保真度更高 |
| 依赖策略 | 零依赖 | 按需引入 | 按需引入 | ChromaDB 值得，其余不引入 |
