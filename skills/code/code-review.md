# 代码审查技能

## 目标
对用户提供的代码或文件进行全面审查，检查安全漏洞、逻辑错误、
可维护性问题和性能隐患。

## 执行流程

### 第一步：了解变更范围
用 `list_files` 查看目录中有哪些文件。
用 `read_file` 读取用户要审查的目标文件。

### 第二步：安全检查（最高优先级）
检查以下安全问题：
- 硬编码的密钥或凭证（API Key、密码、Token）
- SQL 注入风险（用字符串拼接构造的查询）
- 路径穿越风险（未校验的文件路径）
- XSS 漏洞（未转义的用户输入）
- 不安全的 eval/exec 调用

如果发现 CRITICAL 级别问题，标记为 **BLOCK** —— 合并前必须修复。

### 第三步：Bug 和正确性检查
- 逻辑错误、边界条件（off-by-one）
- 缺少错误处理
- 类型不匹配
- 并发竞争条件（如果是异步/多线程代码）

### 第四步：代码质量和可维护性
- 函数过长（>50 行）？建议拆分
- 文件过大（>800 行）？建议提取模块
- 嵌套过深（>4 层）？建议用 early return
- 命名不清晰？建议更好的名字
- 缺少测试？标记出来

### 第五步：生成审查报告
以结构化格式输出：

| 严重度 | 文件 | 行号 | 问题 | 建议 |
|--------|------|------|------|------|
| CRITICAL | ... | ... | ... | ... |
| HIGH | ... | ... | ... | ... |
| MEDIUM | ... | ... | ... | ... |
| LOW | ... | ... | ... | ... |

## 规则
- 不要标记风格偏好问题（空格 vs Tab、单引号 vs 双引号）
- 如果代码已有测试，说明测试质量
- 每条问题都要附带改进建议，不要只批评不给方案
